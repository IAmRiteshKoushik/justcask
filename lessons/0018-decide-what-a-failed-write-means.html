Decide what a failed write means

Lesson 17 stopped a partial record from entering the keydir. The physical file may still end with those partial bytes. Decide what the process does next.

The state we must not ignore

valid record A | valid record B | partial record C | EOF

Append has returned an error for record C, so the keydir has no location for it. That is good. But appending record D immediately afterward creates this:

valid record A | valid record B | partial record C | valid record D | EOF

A recovery scan cannot reliably tell where C ends and D begins. A short record is only a harmless crash tail when it is at physical EOF.

Choose a policy

PolicyRuleWhat you must prove
Poison the active fileAfter any failed write, refuse every later append on this DataFile.No later record can follow an unknown tail. A restart recovery scan ignores the tail at EOF.
Repair the active fileAfter a failed write, truncate back to the offset captured before the write. Only then permit a later append.Truncation reaches exactly the pre-write length, succeeds before appending resumes, and a failed repair also poisons the file.

For this first version, I recommend poisoning the active file. It has a smaller failure surface and makes the invariant easy to test. Repair is a sensible later extension, but it adds another write-like operation whose own failure needs a rule.

Write your decision before code

  1. Choose one policy and add it to DECISIONS.md.
  2. State the new invariant in one sentence. Include what a later Append returns after a prior failed write.
  3. List the first test you would write. For the poison policy, it should force one write failure, call Append again, and prove the fake received no second Write call.

Do not add repair logic yet. The choice comes first. Bring back your one-sentence invariant and test name, then implement only the chosen policy.
