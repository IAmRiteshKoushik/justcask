Separate records from files

The codec knows what valid bytes mean. The data-file layer knows where those bytes live. Keeping those jobs separate is what makes recovery and compaction manageable later.

The next component

Create an internal data-file package in the next implementation step. It owns one open append-only file. It does not parse a key, maintain a keydir, implement a CLI command, or decide whether a record is a put or delete.

record package     valid record ⇄ v1 bytes
data-file package  encoded bytes ⇄ file offset and length
future store       key ⇄ newest data-file location

The write invariant

A future store must follow this order:

encode record → append bytes successfully → publish keydir location

Never publish first. A keydir entry pointing at bytes that failed to write is a successful read of data that never existed.

What append needs to return

The store will later need enough information to read the exact record or value again. At minimum, that is the file identity, the byte offset where the record starts, and the full encoded record size. Offset zero means the first record begins at the first byte of the data file, including its checksum.

Keep durability separate for one lesson. A successful operating-system write means the process handed bytes to the OS. It does not yet promise those bytes survive a power loss. We will add an explicit sync policy after basic append and reopen behavior are correct.
