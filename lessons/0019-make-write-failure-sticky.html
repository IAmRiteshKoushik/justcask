Make write failure sticky

Your failing test says a data file must remember that a write may have left an unknown tail. Now add only the state needed to enforce that rule.

Trace the two calls

Append(first)  → Stat → Write → io.ErrShortWrite → mark poisoned → return zero Location
Append(second) → see poisoned → return zero Location and poison error → do not call Stat or Write

The second call must stop before it touches the underlying file. That is stronger than merely returning an error after another failed write.

Implementation constraints

  1. Add one private boolean state to DataFile. Its zero value must mean healthy.
  2. Add one package error that callers and tests can check with errors.Is.
  3. At the first line of Append, reject a poisoned file with that error and a zero Location.
  4. Set the state only when Write returns an error. A failed Stat did not write bytes, so it does not poison the file.
  5. Keep the existing wrapped write error for the first failed append. It still needs to preserve io.ErrShortWrite.

Strengthen the test after it turns green

Once you name the poison error, change the second-call assertion from “non-nil” to errors.Is(err, yourPoisonError). Keep the writeCalls == 1 assertion. The pair proves the public result and the lack of I/O.

Stop point

Run mise exec -- go test ./internal/datafile. Then explain why a Stat failure remains retryable but a Write failure does not. That distinction is the whole policy.

Primary source: Go's os.File.Write documentation. It defines the write result your code must treat as dangerous.
