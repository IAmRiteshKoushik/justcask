When a checksum means stop

A checksum does not prevent a crash. It lets recovery distinguish bytes it can trust from bytes it cannot.

Two failures that look similar

Crash tail. The decoder reads a valid header near EOF, but the file ends before the declared key and value bytes arrive. This is expected after an interrupted append. The record was never valid, so it must not affect the keydir.

Corrupt complete record. The decoder can read every byte the header declares, but the checksum does not match. The database cannot know which of those bytes are trustworthy. Treat this as corruption, surface an error, and do not invent a policy that silently drops an arbitrary middle record.

The checksum should cover the bytes whose integrity matters, normally the header fields after the checksum plus the key and value. Excluding the checksum field itself avoids a circular calculation. Go's `hash/crc32` package is enough for accidental corruption detection. It is not a security feature.

Trace recovery by hand

Assume a data file contains records A, B, and C in that order.

  1. A is complete and its checksum matches.
  2. B has a complete header but EOF arrives before its declared value ends.
  3. C cannot physically exist after B in an append-only file, because B reaches EOF.

Recovery admits A, ignores B as an uncommitted tail, and finishes. Now replace B with a complete record whose checksum fails. Recovery should return an error rather than continue.

Your format decision

Send a compact proposal. Be exact, but do not write Go yet.

  1. Pick fixed widths for checksum, timestamp, key length, and value length. Name the byte order.
  2. State the exact byte range your checksum covers.
  3. Write the two recovery outcomes: short read at physical EOF, and checksum mismatch after a complete read.
