Prove the policy is not about short writes

The code now poisons a data file for every write error. Make the test prove that the rule is about uncertain file state, not the special name io.ErrShortWrite.

Change one test input

In TestAppendRefusesLaterWritesAfterWriteFailure, replace the first write's io.ErrShortWrite with a new sentinel error local to the test, such as an injected I/O failure. Keep the partial byte count if you want, but the test's point is the error identity.

Name the caller-visible state

Rename the poison sentinel to say what happened to what. A reader at a call site should not need to open its declaration to learn that the active data file is poisoned.

Retrieval check

Why does the second append return the poison error instead of repeating the first injected write error? Answer in one sentence, then run mise exec -- go test ./internal/datafile.

Primary source: Go's io.Writer contract. It gives io.ErrShortWrite a specific meaning. Your active-file policy deliberately covers more than that case.
