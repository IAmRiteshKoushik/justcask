Design a recovery scan

A restart has no in-memory keydir. It must walk the data file from byte zero, recover complete records, and stop only when the file ends in a plausible crash tail.

The scanner's loop

offset = 0
read fixed header at offset
learn the record's declared full length
read exactly that many bytes
decode and validate checksum
publish recovered location
advance offset by the full length

The scanner cannot call the current record.Decode on the whole remaining file. Decode accepts exactly one record. Recovery must first discover the next record's boundary from its header.

Classify the end of a file

Observed bytes at the current offsetRecovery result
No bytes at allClean EOF. Finish successfully.
Some, but fewer than the 20-byte headerCrash tail. Ignore it and finish successfully.
Full header, but fewer bytes than its declared record lengthCrash tail. Ignore it and finish successfully.
Full declared record, checksum mismatchCorruption. Return an error with the file and offset.
Full header with a key or value length beyond the configured limitsCorruption. Return an error. Never allocate from untrusted lengths.

One design task before code

Write down the smallest record-package API that lets the scanner read a header and obtain the full record length safely. It must not expose mutable format constants merely to make the scanner compile.

Then name the first recovery test:

two complete records + every possible truncated prefix of a third record
→ recover the first two locations
→ return no error

Retrieval check

Why is a checksum mismatch in a complete record corruption, while an incomplete record at physical EOF is tolerated? Answer before designing the API.

Primary sources: Go's io.ReadFull documentation and Go's os.File.ReadAt documentation.

Ask for a review of your API sketch before you write the scanner. A good recovery boundary is worth more than a fast first implementation.
