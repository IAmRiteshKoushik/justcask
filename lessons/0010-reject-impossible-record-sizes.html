Reject impossible record sizes

A record length field can represent 4 GiB. That does not mean your CLI should accept a 4 GiB key or value. Disk bytes are untrusted input, and the decoder needs an operational limit before the file layer starts reading declared bodies.

Format ceiling versus implementation limit

QuestionAnswer
What can the v1 field represent?An unsigned 32-bit length, up to 4 GiB minus 1 byte.
What should Justcask accept today?A deliberately smaller bound, tested and documented as an implementation policy.
When must decode enforce it?Immediately after reading the length fields, before computing a body read, allocating, slicing, or verifying a checksum.

Choose a starting policy

For this CLI, I recommend a maximum key size of 4 KiB and a maximum value size of 16 MiB. A 4 KiB key is generous for a key-value store. A 16 MiB value is enough for a serious demo while keeping accidental memory and disk use bounded. These are implementation limits, not a change to the v1 byte layout.

You may choose different values if you can state the workload that needs them.

Test the check before the body exists

Add a stable ErrRecordTooLarge. Then write two tests that begin with a 20-byte header and declare a key or value one byte over its chosen maximum. The body does not need to be present and the CRC does not need to match. The decoder should return ErrRecordTooLarge first, because the declared size itself is unacceptable.

This test order matters. If decode tries to read or allocate the declared body before checking the limit, a corrupt header controls your resource use.

Your task

  1. Reply with your maximum key size and value size. You can accept 4 KiB and 16 MiB or propose your own.
  2. Explain in one sentence why this must be a decoder check rather than only a CLI-input check.
  3. Do not write the tests yet. After your decision, we will add the error and tests together.

The v1 field format is unchanged. When we accept a policy, it goes into DECISIONS.md as a safety limit.
