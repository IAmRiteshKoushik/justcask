Treat every write error as ambiguous

Your poison policy protects a file whose tail might contain incomplete bytes. The trigger is any non-nil write error, not one named error value.

The tempting but incomplete rule

if errors.Is(err, io.ErrShortWrite) {
    poison the file
}

This handles the fake used in your first test. It does not match the decision in DECISIONS.md, which says a data-file write failure poisons the file.

Why error identity is the wrong classifier

io.ErrShortWrite tells you one specific thing: the writer accepted fewer bytes than requested. A disk write may return a different error after accepting zero bytes, some bytes, or an amount the caller cannot safely rely on. The caller does not need to diagnose the operating-system cause. It only needs a safe rule for the active file.

For v1, that rule is conservative and simple:

non-nil error from Write → poison the DataFile → return zero Location

Your patch

  1. In the existing Write-error branch, make poisoning unconditional.
  2. Keep wrapping and returning the original write error. The first failed append must still support errors.Is for its cause.
  3. Rename the poison sentinel so its meaning is clear at a call site. A name that names the data file and its poisoned state is better than a generic “poison error.”
  4. Change the test fake to return a new sentinel error that is not io.ErrShortWrite. The second append must still return the poison error and leave writeCalls at one.
