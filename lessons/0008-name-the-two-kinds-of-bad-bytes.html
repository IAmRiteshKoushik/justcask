Name the two kinds of bad bytes

“Decode failed” is not enough information for recovery. An incomplete final append is normal after a crash. A complete record whose checksum fails is corruption. The caller needs to tell them apart.

Two errors, two later policies

Decoder seesDecoder returnsLater file scanner does
Fewer than 20 header bytes, or fewer bytes than the declared record lengthErrIncompleteRecordIgnores it only if it is at physical EOF of the active file
A full declared record but CRC-32/IEEE differsErrChecksumMismatchStops opening and reports corruption. It never silently discards the record.

These should be stable package errors. Callers should use errors.Is, not compare error strings. Contextual details can wrap the stable error later.

Write tests before changing decode

  1. Add a test that starts with the valid 24-byte vector and removes its final byte. It should expect ErrIncompleteRecord.
  2. Add a test that copies the valid vector, changes only its final value byte, and keeps the stored checksum unchanged. It should expect ErrChecksumMismatch.

Both tests should use errors.Is. They should assert that no valid record is returned. Keep them separate. A test that truncates a record and also corrupts its checksum cannot tell you which check ran first.

Your task

  1. Declare the two stable errors in the record package. Do not change Decode yet.
  2. Add the two tests above and run go test ./internal/record.
  3. Send the failure output. It should tell us which generic return paths must start returning or wrapping the stable errors.

This is the bridge from a byte parser to crash recovery. The recovery scanner arrives only after these distinctions are locked into tests.
