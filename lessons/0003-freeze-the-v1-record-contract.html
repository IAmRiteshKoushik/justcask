Freeze the v1 record contract

Once records reach disk, their layout is an API. Give every field a width, a byte order, and a job before writing the encoder.

Make implicit choices explicit

A four-byte unsigned length permits one field up to 4 GiB. That is far beyond a sensible CLI value limit, but it is still a format limit that the decoder must enforce. A four-byte Unix-seconds timestamp has a 2106 boundary. Use an eight-byte signed or unsigned timestamp if you keep timestamps in v1.

Pick big-endian or little-endian. Either is valid when every encoder and decoder agrees. Big-endian is conventional in on-disk and network specifications because the byte sequence preserves numeric order. Little-endian matches common CPUs. The durable part of this choice is recording it and testing exact bytes.

checksum u32 | timestamp u64 | key length u32 | value length u32 | key | value
      4 B     |      8 B      |      4 B       |       4 B        | variable

This layout has a 20-byte fixed header. The checksum covers every following header field plus key and value, but never the checksum's own four bytes.

Corruption is not a deletion request

On a complete record with a checksum mismatch, opening the database should return an error with the segment filename and byte offset. It should not truncate, compact, or delete anything. The only automatic tail case is a short read at physical EOF, where no later bytes exist and the partial record never enters the keydir.

Design pressure. Why not truncate after any checksum failure? Because the failure may occur in the middle of a file. Truncating there could discard intact later records and turn detectable corruption into silent data loss.
